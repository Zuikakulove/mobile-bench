## 0. 記述の確からしさの区別

本文の主張には、どこまで確認したかを次の印で示す。

| 印 | 意味 |
|---|---|
| 【コード】 | このリポジトリのコードを読んで確認した(ファイル:行を併記) |
| 【実行】 | この調査で実際に動かして確認した(ビルド、テスト、シミュレーション、コンパイル結果の比較) |
| 【資料】 | 公式資料などの一次情報を原文で確認した(出典は §7) |
| 【検索】 | Web 検索結果の要約で確認した。原文は読んでいない(出典は §7) |
| 【推測】 | 未確認。一般知識や推論に基づく |
| 【要実機】 | 実機でしか確かめられない(方法は §6) |

用語は次の意味で使う。

- **単位**: テストが繰り返す仕事の最小のまとまり(篩 1 回、行列積 1 回など)。
- **窓**: 単位数を数える時間の区切り。
- **段階**: 計測条件の区分。現行は「ピーク」と「持続」の 2 つ。

現行の計測手順(0.2.0)【コード】:

1. **準備**: 全コアに 100 ms 負荷をかけた直後の実効クロックを基準として記録する。
2. **ピーク**: 各テストの前に 2 秒以上休み、実効クロックが基準の 95% 以上に戻るまで待つ(最大 60 秒)。
3. **持続**: 全コアに 3〜10 秒負荷をかけてクロックが落ち着くのを待ち、休まず全テストを測る。
4. **安定判定**: 本計測 5 回の (最大 − 最小) ÷ 中央値が 6% を超えたら測り直す(最大 2 回)。最もばらつきの小さい回を採用する。

### 1.5 コードを読んで気づいた点

設計判断に関わるものだけを挙げる。

1. **マルチスレッドの固定 16 単位は、非対称構成で大きな誤差を出す。** 最後の数単位を遅いコアが取ると、速いコアは仕事がなくなって待つだけになり、遅いコアの終了が全体の時間を決める。§1.6(b) のシミュレーションでは、基準機と同じ「速いコア 4 + 遅いコア 4」の型で、経過時間が理想の 1.01〜1.49 倍になった。しかも、速度比が少し違うだけで値が大きく変わる。速いコア 2 + 遅いコア 6(LG 端末の 765G の型)では 1.38〜1.62 倍、8 Elite の型では 1.09 倍である。誤差の大きさが端末ごとに違うので、端末同士のスコアの比がその分だけ狂う。D3 の固定時間方式で解消できる。
2. **iOS のツールチェーンが固定されていない。** `ios.yml:18` は `macos-latest` を使う。このラベルは現在 macOS 26 を指し、既定の Xcode は 26.6、Clang は 21.0.0 である【資料】。GitHub がラベルの指す先を変えると、コンパイラが黙って変わる。Android 側は NDK 27.2.12479018 に固定されている(`android/app/build.gradle.kts:17`、`android.yml:40`)。
3. **iOS のフラグ検査は表示だけ。** Android は `check_android_flags.py` が全ソースのフラグを検査して失敗させるが、iOS は設定をログに出すだけである(`ios.yml:39-44`)。
4. **計測中の中断が結果に反映されない。** アプリがバックグラウンドに回っても計測は「有効」のまま終わる。Android・iOS ともライフサイクルを見るコードがない【実行: 全ソースを検索】。
5. **計測スレッドの優先度設定が 2 層に分かれている。** 生成したワーカーは core が QoS を設定する(`worker_pool.cpp:36`)。しかしワーカー 0 を兼ねる呼び出しスレッドは、iOS では Swift 側(`BenchmarkViewModel.swift:71`)、Android では Kotlin の `Dispatchers.Default`(`BenchmarkViewModel.kt:60`)に任されている。
6. **ピークの「回復」は開始時の状態が基準。** 開始時にすでに端末が制限された状態だと、基準クロックが低く測られ、低い状態のまま「回復済み」と判定される。
7. **計測用ビルドがデバッグ構成。** Android は `assembleDebug`(`android.yml:46`)、iOS は `-configuration Debug`(`ios.yml:49`)。core は構成に関係なく `-O2` でコンパイルされるので計測区間への影響は小さいと考えられる【推測】。
8. **無効なスコアが 0 で出る。** 無効なテストのスコアは 0.0、総合も 0 になる(`runner.cpp:347,409`)。「動かない端末」を表すには 0 と区別できる表現が必要である(§4-Q8)。
9. **バージョンが 3 か所に手書きされている。** `core/include/mobilebench/version.h`、`android/app/build.gradle.kts`、`ios/project.yml`。一致を検査する仕組みはない。
10. **iOS の機種情報が不足している。** `git_sha` と SoC 名を渡していないため、要約に `?` と出る(`BenchmarkViewModel.swift:114-130`)。充電状態と電池残量も iOS では記録していない。
11. **計測区間に libc の `memset` がある。** 篩は区間ごと(`cpu_sieve.cpp:53`)、行列積は単位ごと(`cpu_matmul.cpp:84`)。比率は 1% 未満と見積もれるが【推測】、実装は OS ごとに違う。
12. **公開リポジトリにデバッグ署名鍵がある。** `android/app/debug.keystore`。上書き更新のための意図的な構成である(`android/app/build.gradle.kts:48-56`)。この鍵は誰でも入手できるので、同じアプリ ID を名乗る別の APK を、このアプリの更新としてインストールさせることが技術的には可能である。配布用の署名には使えない。

### 1.6 この調査で行った検証【実行】

**(a) ビルドとテスト。** clang 18.1.3(x86_64)で core をビルドし、3 つの CTest がすべて成功した(約 58 秒)。CLI の全計測は約 63 秒で、1 単位は 4 テストともおおむね 35〜80 ms だった。共有環境のため実行のたびに 2 倍程度ぶれ、全テストが「不安定」と判定された。この環境の数値は、端末の性能の目安にはならない。

**(b) 固定仕事量方式の誤差のシミュレーション。** 全ワーカーが共有カウンタから 1 単位ずつ取り合う現行方式を模擬した。値は「経過時間 ÷ 理想の時間」で、1.0 が理想である。1.50 は、スコアが本来より 33% 低く出ることを意味する。

| 構成(仮定) | 16 単位(現行) | 64 単位 | 256 単位 |
|---|---|---|---|
| 速いコア 4 + 遅いコア 4、速度比 2.5(基準機の型) | 1.06 | 1.10 | 1.04 |
| 同、速度比 3.0 | 1.01 | 1.01 | 1.00 |
| 同、速度比 3.5 | 1.14 | 1.13 | 1.05 |
| 速いコア 2 + 遅いコア 6、速度比 2.5(LG 端末の 765G の型) | 1.38 | 1.04 | 1.03 |
| 同、速度比 3.0 | 1.50 | 1.12 | 1.03 |
| 同、速度比 3.5 | 1.62 | 1.02 | 1.02 |
| 速いコア 2 + やや遅いコア 6、速度比 1.3(8 Elite の型) | 1.09 | 1.07 | 1.01 |
| 同じコア 8 | 1.01 | 1.01 | 1.00 |

基準機の型(4 + 4)は、速度比によって値が大きく動く。16 単位のとき、速度比 2.0 で 1.49、2.5 で 1.06、3.0 で 1.01、3.5 で 1.14、4.0 で 1.27 だった。3.0 で誤差が小さいのは偶然である。速いコアが 3 単位こなす間に遅いコアが 1 単位こなし、4 × 3 + 4 × 1 でちょうど 16 単位を使い切る。実機の速度比がここから少しずれるだけで、誤差は 1 割を超える。

固定時間方式(速いコア 4 + 遅いコア 4、速度比 3.0)で「計測したスループット ÷ 真のスループット」を求めた結果:

| 窓の長さ(遅いコアの 1 単位の何倍か) | 締切で実行中の単位を捨てる | 実行中の単位を完了させ、実時間で割る |
|---|---|---|
| 1.7 倍 | 0.83 | 1.00 |
| 6.7 倍 | 0.96 | 1.00 |
| 16.7 倍 | 0.98 | 1.00 |
| 66.7 倍 | 0.996 | 1.00 |

速度比は仮定である。基準機の実際の値は【要実機】(§6 V2)。周波数の変化やスレッドの移動は模擬していない。

**(c) ターゲット設定による生成コードの違い。** 行列積の最内ループ(`cpu_matmul.cpp:39`)を抜き出し、同じ `-O2 -ffp-contract=on` で arm64 向けにコンパイルした。

| ターゲット設定 | 既定の対象 CPU | 最内ループの積和命令 |
|---|---|---|
| `aarch64-linux-android26` | generic | 2 本(1 反復で double 4 個) |
| `arm64-apple-ios16.0` | apple-a7 | 2 本(同上) |
| `arm64-apple-ios16.0 -mcpu=apple-a14` | apple-a14 | **4 本**(1 反復で double 8 個) |

同じソース・同じフラグでも、対象 CPU の指定で機械語が変わる。これは Ubuntu の clang 18.1.3 での結果であり、NDK の clang や Apple clang そのものでは確認していない。Apple clang の既定の対象 CPU は【推測】の域を出ない(§6 C1)。

**(d) 単位を小さくしたときの挙動**(x86_64 の開発環境、参考値)。

| 篩の上限 | 1 単位 | 現行との比 |
|---|---|---|
| 40,000,000(現行) | 60 ms | 1 |
| 2,000,000 | 3.2 ms | 1/19 |
| 1,000,000 | 1.6 ms | 1/37 |
| 500,000 | 0.9 ms | 1/66 |

| 行列積の n | 作業領域(行列 3 枚) | 1 演算あたりの速さ |
|---|---|---|
| 576(現行) | 7,776 KiB | 3.5 GFLOPS |
| 256 | 1,536 KiB | 3.3 GFLOPS |
| 192 | 864 KiB | 5.7 GFLOPS |
| 128 | 384 KiB | 9.4 GFLOPS |

篩は上限にほぼ比例して単位が小さくなる。行列積は n を小さくすると 1 演算あたりの速さ自体が変わる。キャッシュに収まるためで、テストの性格が変わることを意味する(§4-Q5)。絶対値は (a) と同じ理由でぶれるので、見るべきは比である。

## 2. 「スコアが同じ意味を持つ」の定義

本書では次のように定義する。以降の判断はこの定義に照らして行う。

> スコアは、**同じ入力・同じ手順・検証済みの同じ出力**を持つ仕事を、**同じ長さの時間**でどれだけこなせたかを、基準機との比で表したものである。

| 両 OS で同じにするもの | 端末の性能の一部として受け入れるもの |
|---|---|
| 仕事の定義(アルゴリズム、入力、単位の大きさ) | OS のスケジューラがスレッドをどのコアに置くか |
| 計測手順(窓の長さ、回数、代表値、待機と安定の判定) | 電力・発熱の制御(メーカー独自のものを含む) |
| CPU カーネルの機械語(できる限り。§4-Q2) | GPU ドライバとシェーダーコンパイラの出来 |
| GPU のシェーダー(単一ソース)と描画命令の列 | GPU 内部の動作(タイル方式の隠面消去など) |
| 出力の検証(チェックサム、画像の照合) | メモリやキャッシュの構成 |

もう 1 つの原則として、**片方の OS でしか取れない情報は、スコア・待機の判定・有効性の判定のどれにも使わない。** D6 を一段広げたもので、現行実装はすでに満たしている(`README.md:104`)。

## 3. 決定事項と具体化

各決定について、具体化した内容と、将来見直す条件を記す。異議と補足は §3.8 にまとめる。

### D1. スコアの基準(基準機を各テスト 1000 点、総合は幾何平均)

- **基準機**(2026-11-11 に変更): Nothing Phone (1)。変更前は、Snapdragon 765G を搭載した LG 端末だった。
- **変更の理由**(依頼者からの情報): LG 端末は OTA の提供が終わっている。今のファームウェアは LGUP で書き込んだもので、Play プロテクトの認定がない。現行の APK もインストールできない。基準機として、同じ条件で測り直せる見込みが立たない。基準値をまだ測っていなかったので、この時点で変更した。
- **基準機の仕様**:

  | 項目 | 内容 | 確認の程度 |
  |---|---|---|
  | SoC | Qualcomm Snapdragon 778G+ 5G(SM7325-AE) | 【検索】 |
  | CPU | Kryo 670、最大 2.5 GHz | 【検索】Qualcomm の製品ページの要約 |
  | コア構成 | 速いコア 4 基(Cortex-A78 系。うち 1 基が 2.5 GHz)+ 遅いコア 4 基(Cortex-A55 系) | 【検索】。残りのコアの周波数は確定できていない(下の注)。【要実機】(§6 V2) |
  | GPU | Adreno 642L | 【検索】 |
  | Vulkan | 1.1(公表値) | 【検索】Qualcomm の資料の要約。ドライバが実際に報告する版は【要実機】(§6 V8) |

  注 1: Qualcomm と Nothing の公式サイトには、この調査の環境から接続できなかった。原文は読めていない(§7)。
  注 2: コアごとの周波数は資料によって違う。検索で確認できた資料は、速いコアの残り 3 基を 2.2 GHz、遅いコア 4 基を 1.9 GHz としている【検索】。2.4 GHz と 1.8 GHz とする資料もあったと記憶しているが、今回は確認できていない【推測】。アプリの要約には各コアの最大周波数が出るので、実機で確定できる。

- **端末の役割**:

  | 役割 | 端末 | 状態 |
  |---|---|---|
  | 基準機 | Nothing Phone (1)(Snapdragon 778G+) | 基準値は未測定 |
  | 第 2 の端末(D2) | 8 Elite 搭載機(HONOR Magic7 RSR) | 使用中 |
  | 低性能側の参考端末 | LG 端末(Snapdragon 765G) | 現行の APK をインストールできない。解決すれば使う(§6 V20)。基準値には使わない |
  | iOS | iPhone | 保留(§8) |

- **スコアの式**(異議 1 を採用):

  ```
  1 単位あたりの時間 = 窓の長さ ÷ その窓でこなした単位数
  スコア = 基準機の 1 単位あたりの時間 ÷ 計測した 1 単位あたりの時間 × 1000
  ```

- **1000 点の定義**: 「基準機がピーク段階で出す値」とする。持続段階も同じ基準値で採点する。持続率を意味のある値にするためで、現行実装と同じである(`reference_times.h:11`)。
- **総合スコア**(異議 2 を採用):
  1. 分野ごとに、その分野のテストのスコアを幾何平均する。
  2. 分野のスコアを、次の重みで幾何平均する。

     | 分野 | CPU シングル | CPU マルチ | GPU | メモリ |
     |---|---|---|---|---|
     | 重み | 3 | 3 | 3 | 1 |

     式で書くと `総合 = (CPUシングル^3 × CPUマルチ^3 × GPU^3 × メモリ^1)^(1/10)`。
  3. 総合スコアは、必須の分野がすべて有効なときだけ出す(§4-Q8)。段階(ピーク、持続)ごとに 1 つずつ出す。
- **分野がそろうまでの扱い(案)**: GPU とメモリのテストができるまでは、4 分野がそろわない。その間は、その `benchmark_version` のスイートに含まれる分野だけを必須とし、同じ比の重みで総合を出す。CPU だけの間は、CPU シングルと CPU マルチを 3:3 で平均する。版が違えば総合は比べられないので(D7)、混同は起きない。
- **見直す条件**: 基準機を維持できなくなったとき。主流機のスコアが 5 桁を超えて読みにくくなったとき。基準機の変更は、過去のスコアと比べられなくなる変更として扱う。重みを変えるときは版を上げる(§5.3)。

### D2. 基準値は基準機の実測値を定数として埋め込む

- **具体化(測定手順の案)**:
  1. 条件: 室温 20〜25℃、充電していない、電池 50% 以上、省電力モードはオフ、機内モード、直前 5 分は操作しない。
  2. 5 回実行する(各回の間は 3 分以上)。条件の警告(§4-Q7)が出た回は捨てて測り直す。
  3. 各テストについて、ピーク段階の「1 単位あたり時間の中央値」を 5 回分集め、その中央値を基準値にする。
  4. 5 回分の JSON を `docs/reference/<benchmark_version>/` に保存する。`reference_times.h` には機種名、OS のビルド番号、アプリのビルド番号、測定日をコメントで書く。
- **基準機の要件**(2026-11-11 の変更から得た条件): 正規のファームウェアで動いていること。現行の APK をインストールできること。同じ条件で測り直せる見込みがあること。
- **参考端末の扱い**: LG 端末(765G)で測った値は、基準値に使わない。低性能側の挙動を確かめるための参考として、結果を `docs/reference/` に保存するだけにする。
- **第 2 の端末**(異議 3 を採用): 基準値を測るたびに、8 Elite 搭載機でも同じ手順で測り、結果を同じ場所に保存する。基準機が使えなくなったときは、第 2 の端末との比から新しいテストの基準値を導く。基準機の OS は、測定の時期をまたいで更新しない。更新した場合はビルド番号を記録する。
- **見直す条件**: 基準機を複数にしたくなったとき。

### D3. 固定時間方式

- **採用理由の補強**: 基準機と 8 Elite 搭載機の性能差は数倍あると見込む【推測】。固定仕事量では、遅い端末ほど長く負荷がかかり、電力・発熱制御の影響の受け方が端末ごとに変わる。現行実装はこれを避けるためにマルチの仕事量を 64 → 16 単位に減らした(`core/src/registry.cpp:15-16`)。この方式には §1.5-1 の誤差がある(シミュレーションでは、16 単位のとき、基準機の型で 1.01〜1.49 倍、LG 端末の型で 1.38〜1.62 倍)。固定時間なら全端末が同じ時間だけ負荷を受け、この誤差も出ない(§1.6(b))。
- **具体化**: §4-Q5 と §5.1。
- **見直す条件**: 単位の重さを均一にできないテスト(入力によって 1 単位の重さが変わるもの)を入れたくなったとき。

### D4. GPU テストはオフスクリーン描画

- **具体化**: 描画先の大きさは画面と無関係な固定値にする。窓の終わりで、提出した仕事がすべて完了するのを待つ。
- **注意点**:
  - iOS はバックグラウンドのアプリの GPU 利用を制限する【資料】。計測中はアプリを前面に保ち、バックグラウンドに回ったら計測を無効にする。
  - 計測中は UI の更新を最小限にする。進捗表示の描画も GPU を使うためである【推測】。
- **計測中の表示**: 方針は §5.4。計測そのものは、オフスクリーン・固定解像度のまま変えない。
- **見直す条件**: 画面表示込みの体感(フレームの間隔の安定性など)を測りたくなったとき。その場合も総合スコアとは別枠にする。

### D5. GPU の機能要件は Vulkan 1.1 の範囲

- **具体化**: 「Vulkan 1.1 のコア仕様で必須の機能・上限・フォーマットだけを使う」と定義する。任意機能は、手元の端末が対応していても使わない。Metal 側も同等の機能に限る。
- **根拠**(2026-11-11 に改めた): 古い端末も対象にするためである。Android 10 以降で発売された端末には Vulkan 1.1 への対応が求められている【検索】。これを下限にすれば、数年前の中位機まで GPU テストを動かせる。以前は「基準機(765G の Adreno 620)の上限に合わせる」ことを根拠にしていた。基準機の変更に伴って根拠を改めたが、要件そのものは変えていない。
- **基準機の対応状況**: Adreno 642L は Vulkan 1.1 対応と公表されている【検索】。ドライバが実際に報告する版、機能、上限、フォーマットは【要実機】(§6 V8)。実機がより新しい版を報告しても、使うのは 1.1 の範囲だけである。
- **見直す条件**: 対象にする端末の範囲を見直すとき。Vulkan 1.1 で必須でない機能が、テストに欠かせないと分かったとき。

### D6. Android 専用の情報はスコア計算に使わない

- **具体化**: §2 の原則のとおり、待機の判定と有効性の判定にも使わない。Android 専用の値(周波数、クラスタ構成、電池温度など)は JSON の参考値に留める。
- **見直す条件**: iOS でも同等の情報が公式 API で取れるようになったとき。

### D7. テスト内容を変えたら benchmark_version を上げ、基準値を測り直す

- **具体化**: 版の規則は §5.3。「テスト内容の変更」には、生成される機械語やシェーダーが変わる変更(ツールチェーンの更新など)も含めることを提案する。
- **見直す条件**: 測り直しの負担が大きく、開発が止まるとき(その場合も、版を上げずに計測区間を変えることはしない)。

### D8. iOS と Android の比較は、コンパイラ差を確認できるまで暫定扱い

- **背景**: 基準機は Android だけである。コンパイラが違うことによる速度差は、そのまま iOS のスコアに乗る(§3.8 補足 4)。
- **具体化(案)**:
  - 「確認できた」とする条件は、§4-Q2 の検証 2(カーネルの最内ループの機械語が両 OS で一致)と検証 3(同じハードウェアでの速度比が 3% 以内)がどちらも通ることである。どちらも CI でできる。
  - 暫定の間は、iOS のスコアに「暫定」と表示し、JSON にも記録する。Android 同士の比較は、この決定の対象外である。
  - 確認が済んだら、どの `benchmark_version` から暫定を外したかを本書に記録する。
- **GPU への適用**(2026-11-10 採用): この決定は CPU のコンパイラ差についてのものだが、GPU テストも、§4-Q1 の出力の照合が両 OS の実機で通るまで、同じく暫定扱いにする。
- **見直す条件**: 検証 2・3 が成り立たないと分かったとき(§4-Q2 の D 案に進み、条件を定義し直す)。

### D9. 特定メーカーの省電力制御に合わせて、テストの処理量を変えない

- **対象となる挙動の例**: 短時間だけのブースト、全コア負荷を続けたときのコアの休止や周波数の制限(`README.md:187-190`)、HONOR 端末のタッチ直後だけ高性能になる挙動。
- **具体化**:
  - 単位の大きさ、窓の長さと数、スレッド数を、特定の端末やメーカーの制御の閾値に合わせて決めない。決める根拠は、全端末に共通の規則(§4-Q5)だけにする。
  - メーカーの制御によって計測の途中で状態が変わる端末は、「不安定」の印や低いスコアとして結果に現れる。これは §2 のとおり端末の性能の一部として受け入れる。
  - メーカー固有の挙動を調べること自体は妨げない。診断モードと実機検証(§6 V5)で記録し、結果の注意書きに使う。
- **この決定に反する現行の調整**: 0.2.0 は、8 Elite 搭載機が全コア負荷の約 1 秒後に制限されることに合わせて、マルチの仕事量を 64 → 16 単位に減らしている(`core/src/registry.cpp:15-16`、`README.md:88`)。固定時間方式への移行(D3)で、この調整は廃止する。
- **タッチ直後の挙動について**: 計測は「計測開始」のタッチで始まるので、最初のテストだけ有利になる可能性がある【推測】。処理量では対処しない。現行の手順は各テストの前に 2 秒以上休む(§1.3)。これで影響が消えるかは【要実機】(§6 V5)。
- **待機や判定の値への適用**(2026-11-10 採用): 待機や判定の値(休止の長さ、回復の判定など)も、同じ考え方で特定メーカーに合わせて変えない。
- **見直す条件**: 同じ挙動が多くのメーカーの端末に共通すると分かったとき。その場合は、特定メーカーへの合わせ込みではなく、全端末に共通の定義として見直す。

### 3.8 決定事項への異議と補足

決定を覆すべき欠陥は見つからなかった。ただし、文言の修正か補強が必要な点が 3 つあった。**3 点とも 2026-11-10 に採用され、D1 と D2 に反映した。** 以下は検討の記録である。

**異議 1: D1 の式は、D3 と組み合わせるとそのままでは成り立たない(文言の修正が必要)。**
固定時間方式では計測時間が全端末で同じになる。「基準の時間 ÷ 計測時間 × 1000」を文字どおりに読むと、全端末が同じスコアになる。「時間」を「1 単位あたりの時間」と読み替えれば、趣旨を変えずに成り立つ。

```
1 単位あたりの時間 = 窓の長さ ÷ その窓でこなした単位数
スコア = 基準機の 1 単位あたりの時間 ÷ 計測した 1 単位あたりの時間 × 1000
       = 計測したスループット ÷ 基準機のスループット × 1000
```

**異議 2: 「総合スコアは幾何平均」は、テストを増やす前に取り方を決める必要がある。**
全テストを単純に幾何平均すると、テスト数の多い分野が総合を支配する。CPU 4 本に GPU 3 本とメモリ 2 本を足すと、重みはおよそ CPU 44%、GPU 33%、メモリ 22% になる。テストを 1 本足すたびに重みが変わる。また、動かないテストが 1 本あると幾何平均は定義できない。推奨は次のとおり(§4-Q4、§4-Q8)。

- 分野ごとに幾何平均を取り、分野のスコアを重みつきで幾何平均する。重みは 1 か所で明示する。
- 総合スコアは、必須の分野がすべて有効なときだけ出す。

**異議 3: 基準が実機 1 台に依存する(D2・D7 の運用上の弱点)。**
版を上げるたびにその 1 台で測り直す。故障、紛失、電池の劣化、OS 更新による挙動の変化があると、基準を再現できない。補強として次を提案する。

- 基準値の測定のたびに、第 2 の端末(8 Elite 搭載機)でも同じ手順で測り、結果を一緒に保存する。基準機が使えなくなったら、第 2 の端末との比から新しいテストの基準値を導ける。
- 基準機の OS は、測定の時期をまたいで更新しない。更新した場合はビルド番号を記録する。

**補足 4: iOS と Android を「同じ基準」と言える時期(D8 として決定事項になった)。**
基準機は Android だけなので、コンパイラが違うことによる速度差は、そのまま iOS のスコアに乗る。§4-Q2 の検証(カーネルの機械語が一致することの確認)が終わるまで、iOS と Android の比較は暫定値として扱うのがよい。

**補足 5: GPU の負荷量を基準機に合わせて決めることの帰結。**
基準機で十分な単位数を確保できる軽さにすると、高性能機では 1 フレームが数 ms になり、GPU ではなく CPU 側の提出処理が律速になりうる【推測】。§4-Q5 の「複数単位をまとめて提出する」方式で対処する。

D4・D5・D6・D7 には異議がない。

## 4. 採用した方針と検討の記録(Q1〜Q9)

依頼時に未決だった 9 項目について、比べた選択肢と採用した方針を記す。**ここに書いた推奨は、すべて 2026-11-10 に採用された。**

### Q1. GPU API の共通化

**選択肢**

| | A: OS ごとの標準 API + 単一ソースのシェーダー | B: MoltenVK で Vulkan に統一 | C: 既製の抽象化ライブラリ | D: OpenGL ES を両 OS で使う |
|---|---|---|---|---|
| 構成 | Android は Vulkan 1.1、iOS は Metal。シェーダーは 1 本を書き、ビルド時に SPIR-V と Metal 用に変換する | Vulkan のコードだけを書き、iOS では変換層を通す | WebGPU 実装(Dawn、wgpu)、bgfx、SDL3 GPU など | — |
| 命令列が同じこと | 自前の薄い抽象層で担保する。検証が必要 | 自動的に同じ | ライブラリ内部の変換に依存し、見えにくい | 同じ |
| iOS で測るもの | 実アプリと同じ経路(Metal 直接) | 変換層の出来を含む | 抽象層の出来を含む(両 OS で対称) | 非推奨 API の経路 |
| 外部依存 | ビルド時のみ(変換ツール) | 実行時に MoltenVK | 実行時に大きなライブラリ | なし |
| 保守の見通し | 自前のコード 2 系統 | **MoltenVK は Khronos が非推奨とし、コミュニティのベストエフォート保守に移行**【資料】 | ライブラリの版がベンチマークの定義の一部になる | iOS では将来性がない【推測】 |
| 実装量 | 大(バックエンド 2 つ) | 小 | 中 | 中 |

**決定: A。** 抽象層は、テストが必要とする機能だけの小さなものに留める。

**理由**

1. **目的に合う。** §2 の定義では、GPU ドライバは端末の性能の一部である。iOS の実アプリは Metal を直接使うので、変換層を挟むと「端末の性能」ではなく「変換層を含む性能」を測ることになる。3DMark Wild Life も Android は Vulkan 1.1、iOS は Metal と使い分けている【検索】。
2. **B は土台が弱い。** MoltenVK の README は冒頭で非推奨化を告知している【資料】。同じ文書は iOS 向けには引き続き MoltenVK を推奨しているが、保守はベストエフォートである。後継の KosmicKrisp は macOS が対象で、iOS 向けはまだ提供されていない【検索】。
3. **B は「同じ処理」も保証しない。** MoltenVK は自らを、Vulkan 1.4 の「ほぼ完全な部分集合」の実装だと説明している。機能の大多数は Metal に直接対応するが、少数は追加の描画・コンピュートのステージなどで合成され、ごく少数は非対応である【資料】。使う機能によっては、iOS だけ余分な GPU の仕事が入りうる。また、MoltenVK の版を上げるたびに iOS のスコアが変わりうる。
4. **A の弱点は検証で補える。** 2 系統の食い違いは、下の「保証」と「検証」で検出する。

**「同じ処理をしている」ことの保証と検証**

構造で保証すること:

1. **シェーダーは単一ソース。** GLSL を 1 本書き、SPIR-V に変換する。Metal 用のシェーダーは、その SPIR-V から SPIRV-Cross で生成する【資料: SPIRV-Cross は SPIR-V から Metal 用シェーダーを生成する】。両 OS が同じ中間表現から出発する。変換はビルド時に行い、変換ツールの版を固定する。
2. **テスト本体は単一。** テスト(`core/src/tests/gpu_*.cpp`)は、core 内の抽象層(`mb::gpu::Device` の案)に対して命令を出す。バックエンドは命令を 1 対 1 で各 API に置き換えるだけにする。テスト本体に OS 別の分岐を書かない。
3. **条件を固定する。** 描画先の大きさと形式、深度の形式、アンチエイリアスなし、テクスチャは手続き生成の非圧縮。精度はすべて高精度にする。低精度の指定があると、GPU によって実際の精度と仕事量が変わるためである【推測】。
4. **Metal の高速演算モードを切る。** Metal のシェーダーコンパイラは、IEEE 754 に反しうる最適化を既定で有効にしている(`fastMathEnabled` の既定値は true。iOS 18 以降は `mathMode` に置き換え)【資料】。明示的に無効にして、Vulkan 側と演算の意味を揃える。

実行して検証すること:

5. **出力を照合する。** 整数だけで計算するコンピュートテストは、チェックサムがビット単位で一致することを確認する。描画テストは、最後の出力を縮小して読み戻し、基準画像と許容差つきで比べる。不一致なら無効にする。許容差は【要実機】(§6 V12)。
6. **仕事量を記録して照合する。** 描画呼び出し数、頂点数、描画先の画素数を数えて JSON に出し、期待値と比べる。
7. **CI で自動検査する。** シェーダーを再生成して差分がないこと。低精度指定が混ざっていないこと。ソフトウェア実装の Vulkan(lavapipe)で Vulkan 側を実行し、基準画像と一致すること【検索: lavapipe は GPU のない CI で Vulkan のコードを動かすために使われている】。iOS シミュレータで Metal 側を同様に検査できるかは未確認(§6 C5)。
8. **相互検証(任意、スコア対象外)。** 診断用のビルドで、iOS でも Vulkan 側を MoltenVK 経由で動かし、Metal 側との差を見る。差が小さければ、2 系統が同じ仕事をしている証拠の 1 つになる。

保証できないこと: GPU 内部の動作は同じにできない。タイル方式の GPU は見えない画素の処理を省くことがあり、省き方は GPU ごとに違う【推測】。§2 のとおり、これは端末の性能に含める。

計測の様子を画面に出す方法は §5.4 に記す。

**見直す条件**

- KosmicKrisp が iOS に正式対応し、Vulkan の適合認定を得たとき(B を再評価する)。
- Metal 側の保守を続けられないと分かったとき。
- CI でも実機でも、2 系統の一致を検証する手段が成り立たなかったとき。

### Q2. CPU テストのコンパイラ差

**現状**: Android は NDK 27.2.12479018 の clang を使う【コード】。NDK r27 系の clang は `clang-r522817` 系である【検索】。iOS は GitHub のランナーに入っている Xcode の clang を使い、ランナーの記載では現在 Clang/LLVM 21.0.0 である【資料】。フラグは揃えてあるが、コンパイラの世代は離れている。§1.6(c) のとおり、同じフラグでも対象 CPU の設定で行列積の機械語が変わる。

**選択肢**

| | 内容 | 効果 | 代償 |
|---|---|---|---|
| A | 現状維持(フラグを揃え、コンパイラ名を記録) | 差は残る。大きさは不明 | なし |
| B | スカラーで測るループの自動ベクトル化を止める | スカラーの機械語は版による差が小さい【推測】 | SIMD の性能は別に測る必要がある |
| C | SIMD を測る最内ループを、NEON の組み込み関数で明示的に書く | 命令の選択がほぼ固定される | x86_64 用に同じ結果のスカラー版が要る |
| D | 最内ループをアセンブリで書き、両 OS で同じファイルを使う | 機械語が完全に一致する | 保守が重い。Mac なしでの検証が難しい |
| E | ツールチェーンを固定し、生成コードの一致を CI で検査する | 差の発生を検出できる | CI の整備が要る |

**決定: B + C + E を組み合わせる。D は、E の検査で差が解消しない場合の逃げ道とする。**

**NEON を明示的に書く範囲**

| 対象 | 扱い |
|---|---|
| SIMD 演算そのものを測る最内ループ。現時点では行列積の積和ループ(`cpu_matmul.cpp:39`)と、今後のメモリコピーのループ | NEON の組み込み関数で書く。展開回数も手で固定する |
| スカラー性能を測るループ。篩の消し込みと数え上げ(`cpu_sieve.cpp:57,63`)、今後追加する整数カーネル | 組み込み関数は使わない。ループごとに、自動ベクトル化・インターリーブ・展開をソース内の指定で禁止する |
| 計測区間の外(準備、検証、JSON 生成) | 何もしない |

あわせて守る規則:

- **指定はソースの中に書く。** ループへの指定や組み込み関数で表し、ファイル別のビルドフラグは使わない。CMake と Xcode の 2 系統でずれるのを避けるためである。
- **スコア対象のカーネルは、標準ライブラリに依存しない独立したファイルにする。** libc の `memset` などは OS ごとに実装が違う。コンパイラがループを `memset` 呼び出しに置き換えるのも、ソース内の指定で禁止する。
- **チェックサムが命令の選び方に依存しない入力にする。** 現行の行列積は、積和がすべて整数になる入力を使っており、積和の融合の有無にかかわらずビット単位で一致する(`cpu_kernels.h:50-52`)。この方針を続ける。
- **x86_64 向けには同じ結果を返すスカラー版を置く。** スコアは比較の対象外とする。

**検証の方法(E)**

1. **ツールチェーンを固定する。** NDK は固定済み。iOS は `ios.yml` で Xcode の版を明示的に選ぶ(現在のランナーには Xcode 26.0.1〜26.6 が入っている【資料】)。
2. **生成コードを比べる。** CI で、Android の `.so` と iOS のビルド結果からカーネル関数を逆アセンブルし、最内ループの命令の並びを比べる。差があれば失敗させる。最初は報告だけにし、落ち着いたら必須にする。
3. **同じハードウェアで速度を比べる。** GitHub の macOS ランナー(arm64)で、カーネルを Apple clang と別系統の clang(ランナーに Homebrew の LLVM 20 が入っている【資料】)の両方でコンパイルし、交互に実行して速度比を見る。目標は差 3% 以内。NDK の clang そのものではないので、近似である。
4. **コンパイラの版を JSON に記録する**(実装済み。`build.compiler`)。

**見直す条件**

- 検証 2・3 で、指定を入れても差が残るとき(D に進む)。
- NDK または Xcode を上げて生成コードが変わったとき(D7 に従って版を上げ、測り直す)。

### Q3. スレッドの扱い

**前提の確認**: Apple シリコンでは、スレッドをコアに固定する API(`thread_policy_set` の `THREAD_AFFINITY_POLICY`)は使えず、失敗が返る。Apple の技術サポートも、スレッドをコアの種類に結びつける公式の方法はないと回答している【検索】。コアの割り当てに影響を与える公式の手段は QoS クラスである【資料】。

**選択肢**

| | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | 両 OS とも固定しない。スレッド数は論理コア数。優先度を「前面アプリのユーザー起因の処理」に揃える | 両 OS で対称。実アプリの挙動に近い。Android 専用の情報を使わない | 配置は OS 任せなので、ばらつきは増えうる |
| B | Android だけコアに固定する | Android のばらつきが減る | 非対称。クラスタ情報がスコアに影響する(D6 に反する)。OS に無視されることがある(`README.md:190`) |
| C | スレッド数を高性能コア数に絞る | 遅いコアの影響を除ける | 「高性能コア」の判定に OS 別の情報が要る。端末の全能力を測れない |
| D | OS の性能ヒント API を使う(Android の性能ヒント、iOS の QoS) | メーカー制御に意図を伝えられる | Android と iOS で仕組みが違い、対称にならない |

**決定: A(現行実装の方針を維持する)。**

**統一の中身**

- **固定しない。** スコア対象のテストでは、両 OS ともスレッドをコアに固定しない。`sched_setaffinity` は診断モードだけで使う(現行どおり。`diagnostics.cpp:158`)。
- **スレッド数。** シングルは 1、マルチは論理コア数(Android は構成上のコア数、iOS は `hw.logicalcpu_max`。`platform.cpp:64-78`)。
- **優先度。** iOS は全計測スレッドを QoS `USER_INITIATED` にする。Android は既定の優先度で、アプリが前面にあることを条件にする。
- **設定の場所を core に寄せる。** 呼び出しスレッドの設定も `Runner::run` の入口で core が行う(§1.5-5 の解消)。
- **配置のぶれは時間で吸収する。** 固定時間方式とウォームアップの窓により、スレッドが速いコアに移るまでの時間を計測から外す。足りるかどうかは【要実機】(§6 V15)。
- **配置は記録する。** Android は CPU 番号、両 OS とも実効クロックの推定値を JSON に残す(実装済み)。スコアには使わない。

**理由**: 固定は iOS でできない以上、Android だけ固定すれば非対称になる。OS がどのコアに置くかは §2 のとおり端末の性能に含める。Apple の資料も、スレッドごとに仕事を静的に割り振ると速いコアのスレッドが先に終わってしまうと指摘している【資料】。固定時間方式は各スレッドが時間いっぱい働くので、この問題を構造的に避けられる。

**見直す条件**

- 実機で、配置のぶれが安定判定の基準(現行 6%)を恒常的に超えるとき。
- iOS で論理コア数ぶんのスレッドが全コアに行き渡らないことが分かったとき(§6 V6)。

### Q4. テストの構成

**現行 4 テストの評価**: 篩(整数、L1 キャッシュ内の書き込みが中心)と行列積(浮動小数点、SIMD)は性格が違い、最小構成としては妥当である。弱点は、分野が CPU だけであることと、カーネルが 2 種類しかなく、片方の癖が CPU スコアの半分を左右することである。

**追加の候補と評価**

| 候補 | 測るもの | 両 OS で同じ意味になるか | 評価 |
|---|---|---|---|
| メモリコピー(キャッシュより十分大きいバッファ) | メモリの帯域 | なる。最内ループを明示的に書けば機械語も揃う | **追加する** |
| GPU: 画素シェーダーの演算負荷 | 画素あたりの演算能力 | なる(§4-Q1 の検証を前提) | **追加する** |
| GPU: 頂点・三角形の負荷 | 頂点処理と小さな三角形の描画能力 | なる(同上) | **追加する** |
| GPU: コンピュートシェーダーの整数演算 | GPU の汎用演算 | なる。整数なのでビット単位で検証できる | **追加する** |
| CPU: 整数の混合演算(ハッシュ計算など、分岐なし) | 整数演算器の速さ | なる。直線的なコードでコンパイラ差が小さい【推測】 | 後で検討(CPU スコアの偏りを減らす) |
| CPU: 圧縮(分岐と表引き) | 分岐予測とキャッシュ | なる | 後で検討 |
| メモリ: ランダムな参照の遅延 | メモリの遅延 | **なりにくい**。メモリのページの大きさが OS で違うことの影響を受けやすい【推測】 | 総合には入れない |
| ストレージの読み書き | 記憶装置 | **なりにくい**。ファイルシステム、暗号化、キャッシュ回避の手段が OS で違う【推測】 | 総合には入れない |
| 描画呼び出しの数をこなす負荷 | API とドライバの CPU 側の効率 | **ならない**。API の違いそのものを測る | 総合には入れない |

**採用した構成(1.0 の目標)**

| 分野 | テスト ID(案) | 状態 |
|---|---|---|
| CPU シングル | `cpu.single.sieve`、`cpu.single.matmul` | 既存 |
| CPU マルチ | `cpu.multi.sieve`、`cpu.multi.matmul` | 既存 |
| メモリ | `mem.single.copy`、`mem.multi.copy` | 新規 |
| GPU | `gpu.fill`、`gpu.geom`、`gpu.compute` | 新規 |

総合スコアは、分野ごとの幾何平均を重みつきで幾何平均する。重みは CPU シングル 3、CPU マルチ 3、GPU 3、メモリ 1 と決まった(D1)。メモリを軽くするのは、テストが少ないうえに、結果がメモリの世代でほぼ決まるためである。

GPU テストは、少ない描画呼び出しで重い仕事をさせる。高性能機で CPU 側が律速にならないようにするためである。

**削るもの**

- **スコア対象の 4 テストからは削らない。**
- **拡張予定からストレージを外す**(`README.md:307`)。測るとしても参考値に留める。
- **診断モードを整理する。** ブーストの推移と行列サイズ掃引は、単位の大きさを決めるための調査用である。単位が確定したら削除の候補にする。クラスタ別性能と周波数の記録は、新しい端末の調査に使えるので残す。
- **互換用の `overall_score`**(ピークのスコアと同じ値。`result_json.cpp:224`)は、分野別スコアを入れるときに定義し直す。

**見直す条件**

- CPU のどちらかのカーネルで、OS 間の差が説明できないとき(整数の混合演算を足して偏りを確かめる)。
- GPU テストのどれかが、高性能機で CPU 律速になるとき(負荷の作り方を変える)。

### Q5. 処理単位の粒度とテスト時間

**決め方の規則**

1. **単位は均質にする。** どの単位も同じ重さで、前の単位の結果に依存しない。
2. **単位は自己検証できる大きさにする。** チェックサムを確かめられる仕事のまとまりにする。
3. **締切の扱い。** 各ワーカーは締切を過ぎたら実行中の単位を完了してから止まる。スループットは「ワーカーごとの (完了数 ÷ そのワーカーの実測時間) の合計」とする。§1.6(b) のとおり、実行中の単位を捨てる方式は低めに偏り、この方式は偏らない。
4. **単位の上限。** 最も遅いコアでの 1 単位が、窓の長さの 1/20 以下。窓からのはみ出しを 5% 以内にするためである。基準機で必ず満たす。低性能側の参考端末が使える場合は、そこでも確かめる。
5. **単位の下限。** 最も速いコアでの 1 単位が 100 µs 以上。時刻の読み取り(1 単位につき 1 回)の負担を 0.1% 以下にするためである【推測: 時刻の読み取りは数十 ns】。
6. **窓の長さはテストの定義の一部とする。** 変えたら benchmark_version を上げる。

**初期値の案(すべて実機での確認が前提)**

| 項目 | CPU・メモリ | GPU |
|---|---|---|
| 窓 | 200 ms × 5(その前にウォームアップ 200 ms) | 500 ms × 5(その前にウォームアップ 500 ms) |
| 1 テストの負荷時間 | 約 1.2 秒 | 約 3 秒 |
| 単位 | 篩: 上限 500,000〜1,000,000 の 1 回。行列積: n=576 の 1 回を 81 等分した 1 片 | フレーム番号で内容が決まるレンダーパス 1 回(またはコンピュートの実行 1 回)。重さはどのフレームも同じにする(§5.4) |
| 代表値 | 5 窓の「1 単位あたり時間」の中央値(現行の「5 回の中央値」と同じ考え方) | 同左 |

**根拠**

- **CPU の窓を 200 ms × 5 とする理由。** ピークを「休ませた状態から、約 1 秒の負荷で出せる性能」と定義する。アプリの起動や画面の切り替えのような短い処理を想定した、全端末に共通の定義である。5 つに分けるのは、中央値で外れを除き、途中の状態の変化をばらつきとして検出するためである。当初の案は、8 Elite 搭載機が約 1.1〜1.5 秒で制限に入ること(`README.md:190`)を根拠の 1 つにしていた。D9 により、この根拠は使わない。窓の長さを特定の端末の挙動に合わせて調整することもしない。なお、固定時間にすると負荷の時間が全端末で同じになる。現行方式では、遅い端末ほど負荷が長い。
- **篩は上限を小さくする。** 単位は上限にほぼ比例して小さくなる(§1.6(d))。区間の大きさ(32 KiB)は変えないので、L1 キャッシュ内で動く性格は保たれる。
- **行列積は n を小さくしない。** n を変えるとキャッシュへの収まり方が変わり、別のテストになる(§1.6(d))。n=576 のまま、1 回の行列積を同じ重さの片に分ける。現行のコードは 64 ごとのブロックで 3 重に回している(`core/src/tests/cpu_matmul.cpp:27-44`)。外側 2 重のブロックの 1 組(行 64 本ぶん × 中間の添字 64 個ぶん)を 1 片とすれば、1 回の行列積は 9 × 9 = 81 片になり、どの片も同じ重さである。チェックサムは行列積 1 回が完成するごとに照合する。窓の終わりで途中の行列積は、計測の外で最後まで実行して照合する。
- **単位時間の見積もり。** 8 Elite 搭載機ではシングルの 1 回(4 単位)が 110〜147 ms だった(`README.md:191`)。1 単位は約 27〜37 ms である。基準機の速いコアはその約 3 倍、遅いコアはさらに約 3 倍かかると見込む【推測】。この見込みだと、現行の単位は基準機の遅いコアで約 240〜330 ms になり、200 ms の窓に 1 つも入らない。篩を 1/37(上限 100 万)にすれば約 7〜9 ms で、規則 4(10 ms 以下)を満たす。1/66(上限 50 万)なら約 4〜5 ms になる。8 Elite 側は上限 50 万でも約 0.4〜0.6 ms で、規則 5 を満たす。LG 端末(765G)は基準機より遅いと見込むので【推測】、使える場合はそこでも規則 4 を確かめる。確定には実機の値が要る(§6 V2)。

**GPU の単位と提出のまとめ方**

基準機で 1 窓に 20 単位以上が入る軽さにすると、高性能機では 1 単位が数 ms 以下になり、提出のたびの CPU 側の処理と同期が無視できなくなる【推測】。そこで **1 回の提出に M 個の単位をまとめる**。M はウォームアップ中に、1 回の提出が 20〜50 ms になるように 1、2、4、8…から選ぶ。単位の中身(1 つのレンダーパス)は全端末で同じで、変わるのは 1 回の提出に含める個数だけである。選んだ M は JSON に記録する。基準機より遅い端末では、1 窓に入る単位が 20 を下回ることがある。その場合も M は 1 のままで、数え方は変えない。

**見直す条件**

- 実機で、遅いコアの 1 単位が規則 4 を満たさないとき(単位を小さくする)。
- 多くの端末で、窓の長さが原因で受け入れ基準(§4-Q7)を満たせないとき。特定の端末だけで起きる場合は、D9 により窓を変えず、その端末の結果を「不安定」として扱う。

### Q6. 発熱による性能低下の扱い

**前提の整理**: 性能が下がる現象には、時間の長さが違う 3 種類がある。

| 時間の長さ | 現象 | 現行での扱い |
|---|---|---|
| 1〜2 秒以内 | 短時間のブーストとその終了 | ピーク段階 |
| 数秒〜数十秒 | メーカーの電力制御による制限(8 Elite 搭載機では全コア負荷の約 1 秒後から。`README.md:187-190`) | 持続段階 |
| 数分〜数十分 | 本体の温度上昇による制限 | **測っていない** |

現行の「持続」は、温度が上がりきった状態ではなく、数秒の負荷をかけた後の状態である。

**選択肢**

| | 内容 | 評価 |
|---|---|---|
| A | ピークだけを測る | 実使用との差が大きい端末を見逃す |
| B | ピークと持続を別スコアにする(現行) | 短時間の制限まで捉えられる。温度による制限は捉えられない |
| C | 1 回の長い連続実行から、最初と最後を取り出す | 手順は単純。全テストでこれを行うと計測が長くなる |
| D | B に加え、任意で実行する長時間モードを設ける | 3 種類すべてを捉えられる。長時間モードは条件に左右されやすい |

**決定: D。**

1. **ピークと持続は別スコアのままにする**(現行を維持)。各段階で総合スコアを 1 つずつ出し、持続率を併記する。
2. **2 つを 1 つの数字に混ぜない。** 混ぜ方に根拠のある重みがないためである。単一の代表値が必要な場面ではピークの総合を使い、必ず持続率を添える。
3. **表示名を変える。** 現行の「持続」は、温度が上がりきった状態と誤解されやすい。「持続(短時間)」などとする。JSON のキー `sustained` は変えない。
4. **長時間モードを後から足す**(任意実行、総合スコアには入れない)。全コアの CPU 負荷と GPU 負荷を交互に、10〜20 分繰り返す。出すのは、周回ごとのスコアの推移、最高と最低、安定度(最低 ÷ 最高)、発熱状態の推移である。3DMark の Wild Life Stress Test も、同じ場面を 20 分繰り返して推移を見せる形式である【検索】。

**長時間モードを総合に入れない理由**: 温度が上がった状態の性能は、室温、ケースの有無、充電の有無、開始時の温度に左右される。同じ端末でも再現しにくく、§2 の「同じ意味」を満たしにくい。

**測り方の補足**

- **両段階で窓の長さと回数を同じにする。** 持続率が、状態の違いだけを表すようにするためである。
- **発熱の状態は記録するだけ**で、スコアには使わない。Android は発熱状態と余裕度、iOS は `ProcessInfo.thermalState` を記録している(実装済み)【コード】【資料】。
- **開始時に発熱状態が通常でない場合は警告を付ける**(§4-Q7)。

**見直す条件**

- 基準機や iPhone で、現行の回復待ちや事前負荷(3〜10 秒)が意図どおりに働かないと分かったとき(§6 V7)。
- 長時間モードの結果が、条件を揃えても再現しないとき(周回の長さや指標を見直す)。

### Q7. 計測の信頼性

**現行の仕組み**【コード】: 5 回の中央値を採る。(最大 − 最小) ÷ 中央値が 6% を超えたら最大 2 回測り直し、ばらつきが最小の回を採用する。それでも超えていれば「不安定」の印を付ける。チェックサムが合わなければ無効にする。

**決定: 現行の仕組みを固定時間の窓にそのまま移し、足りない部分を足す。閾値は実機のデータなしに変えない。**

**1. 結果の状態を 3 つの軸に分ける**

| 軸 | 意味 | 立つ条件 | 表示 |
|---|---|---|---|
| 有効(`valid`) | 計測が成立した | チェックサム一致、最後まで完了、最適化ビルド、中断なし | 満たさなければスコアを出さない |
| 安定(`stable`) | ばらつきが基準以内 | 現行の判定 | 満たさなければ「参考値」 |
| 条件(`conditions`) | 計測環境に問題がない | 下の警告が 1 つもない | 警告があれば理由つきで「参考値」 |

3 つとも満たし、実機(arm64)の正式ビルドであるものだけを「比較可能」と表示する。

**2. 条件の警告(両 OS で取れる情報だけを使う)**

- 開始時または終了時に、発熱状態が最も低い段階でない。
- 省電力モード(iOS は低電力モード)がオン。
- 充電中、または電池残量が少ない(iOS での取得は追加が必要。§1.5-10)。
- ピークで、待っても回復しなかった(記録は実装済み。`recovered`)。
- 持続で、事前負荷が上限時間で打ち切られた(記録は実装済み。`settled`)。
- 開始時の基準クロックが、その端末でこれまでに記録した最高値の 90% 未満。最高値はアプリ内に保存する。§1.5-6 の対策であり、クロックの推定は両 OS で同じ方法なので対称である。

**3. 中断を無効にする**: 計測中にアプリが前面を離れたら計測を中止し、無効にする(§1.5-4)。

**4. 待ち時間の上限**: 回復待ちは現行でテストごとに最大 60 秒、測り直しを含めると最大 3 回ある。テストを 9 本に増やすと、最悪で 30 分近くかかる計算になる。全体の待ち時間に上限(例: 3 分)を設け、超えたら「回復せず」と記録して先に進む。

**5. 複数回の実行**

- 通常の計測は 1 回で結果を出す(窓 5 つの中央値と、測り直しで安定を確保する)。
- 基準値の測定と公表用の測定は、5 回実行して中央値を採る(§3 D2)。
- アプリに「3 回連続で測って中央値を出す」機能を足すかは、後で決める。

**6. 異常値の検出**

| 対象 | 方法 |
|---|---|
| 窓 1 つだけの外れ | 中央値が吸収する。外れた窓の数を記録する |
| テスト全体の不安定 | 現行の判定(6%)と測り直し |
| ありえない結果 | マルチのスコアがシングルを下回る、単位を 1 つも処理しなかったワーカーがいる、などを警告にする |
| 計測の不成立 | チェックサムの不一致、最適化なしのビルド、中断は無効 |
| 比較できない環境 | シミュレータ、エミュレータ、x86_64 は「比較不可」と表示する |

**7. 受け入れ基準(実機で確認して確定する)**

同じ端末で条件を揃え、間隔を空けて 10 回実行する。目標は、各テストのスコアの変動係数がピークで 2% 以下、持続で 3% 以下である。満たさないテストは、基準値を確定する前に単位と窓を見直す(§6 V14)。

**ばらつきの判定方法の比較**

| 方法 | 利点 | 欠点 |
|---|---|---|
| (最大 − 最小) ÷ 中央値(現行) | 単純。状態の変化を鋭く拾う | 1 つの外れで測り直しになる |
| 最大と最小を除いた 3 つの幅 | 外れ 1 つに強い | 状態の変化を見逃すことがある |
| 中央値からの偏差の中央値 | 統計的に頑健 | 5 点では粗い |

現行の方法は、実機データをもとに決められている(`README.md:185`)。新しいデータなしに変える根拠がないので維持する。固定時間方式に移した後、実機データを見て再検討する。

**見直す条件**: 受け入れ基準を満たせないとき。測り直しが頻発して計測時間が延びるとき。

### Q8. テストが動かない端末の扱い

**選択肢**

| | 内容 | 評価 |
|---|---|---|
| A | 動かないテストがあれば総合スコアを出さない。動いた分野のスコアは出す | 比較の公平さを保てる |
| B | 動いた分野だけで総合を計算する | 完走した端末の総合と見分けがつかず、誤解を生む |
| C | 動かないテストを 0 点や低い点にする | 幾何平均が 0 になる。意味のない値になる |
| D | 別の API(OpenGL ES など)で代わりのテストを動かす | 別の仕事を測ることになり、§2 に反する |

**決定: A。**

1. **テストごとに状態を持たせる。** `ok` / `unsupported`(非対応)/ `failed`(実行時の失敗)/ `skipped`。非対応と失敗には理由を付ける(例: `vulkan_version<1.1`、`timeout`)。
2. **スコアが出せないときは 0 ではなく「値なし」にする。** JSON では `null`、画面では「—」。0 は実測の結果と区別できないためである(§1.5-8)。
3. **分野のスコアは、その分野の全テストが `ok` のときだけ出す。総合は、必須の分野がすべて出たときだけ出す。**
4. **実行前に対応を調べる。** `mb::BenchmarkTest` に、対応状況を返す関数を足す(§5.1)。GPU なら、Vulkan の版、必要な機能・上限・フォーマットを調べる。
5. **実行時の失敗に備える。** GPU の仕事が一定時間で終わらなければ、そのテストを `failed` にして次へ進む。

**個別の扱い**

| 端末 | 扱い |
|---|---|
| Vulkan 1.1 に対応しない Android 端末 | GPU 分野は `unsupported`。総合は出さない。CPU とメモリの分野スコアは出す。Android 10 以降で発売された端末は Vulkan 1.1 対応が求められている【検索】 |
| 32 ビットのみの端末 | 対象外(現行どおり。`android/app/build.gradle.kts:30`) |
| メモリが足りない端末 | メモリテストは確保の可否を事前に調べ、足りなければ `unsupported` |
| シミュレータ、エミュレータ、x86_64 | 動かすが「比較不可」と表示する |

**見直す条件**: 非対応の端末が利用者の多くを占めると分かったとき(「CPU のみ」の別枠の総合を設けるかを検討する)。

### Q9. iOS 版の実装方針

iOS 版の骨格はすでにある(§1.2-3)。残る論点は、実機で動かす手段と、既存部分の固め方である。

**C++ コアの共有方法**

| | 内容 | 評価 |
|---|---|---|
| A | Xcode のターゲットに `core/src` を直接入れてコンパイルする(現行。`ios/project.yml:20-25`) | 単純。フラグの定義が CMake と 2 か所になる |
| B | CMake で core を静的ライブラリにして、Xcode から使う | フラグの定義が 1 か所になる。ビルドが 2 段になる |
| C | Swift Package にする | フラグの指定に制約がある【推測】 |

**決定: A を維持する。** フラグが 2 か所になる問題は、(1) iOS にもフラグの検査を足す、(2) カーネルのコード生成に関わる指定をソース内に書く(§4-Q2)、の 2 つで抑える。GPU を足すときは、Vulkan 用のファイルを iOS の対象から、Metal 用のファイルを Android の対象から外す指定が要る。

**Swift 側の構成**: 現行の「UI は core の JSON を表示するだけ」を維持する(ViewModel、ブリッジ、JSON のデコード、画面の 4 つ)。足すのは次の点である。

- ライフサイクルの監視(前面を離れたら計測を中止して無効にする)。
- 充電状態と電池残量の記録、`git_sha` の受け渡し。
- 計測スレッドの QoS 設定を core 側に寄せる(§4-Q3)。

**ビルドと署名**

前提: 開発はすべて GitHub Actions で行い、PC を使わない(`README.md:7`)。

| | 方法 | PC なしで可能か | 評価 |
|---|---|---|---|
| A | Apple Developer Program(有料)に入り、Actions から TestFlight に送る | 可能と見込む【推測】 | **採用**(登録は保留中) |
| B | 無料の Apple アカウントで署名する | 不可。プロファイルが 7 日で切れ、端末も 3 台までである【資料】。TestFlight は有料会員向けである【検索】。入れ直しには Xcode が要る【推測】 | 不採用 |
| C | 有料アカウントで署名し、IPA を直接配る(アドホック配布) | 可能だが、端末の登録と配布用ページの用意が要る【推測】 | A が使えない場合の代替 |

**決定: A。ただし Apple Developer Program への登録は保留しており、実機向けの作業(下の手順 1〜6)は後回しにする。** 再開は依頼者の指示を待つ。手順の案は次のとおり。細部は【推測】であり、CI で試して確定する(§6 C7)。

1. 依頼者が Apple Developer Program に登録する(年会費が必要)。
2. App Store Connect でアプリを登録し、API キーを発行する。現在の識別子 `com.mobilebench.app`(`project.yml:28`)が使えるとは限らないので、固有の識別子を決める。
3. API キーを GitHub の暗号化されたシークレットに登録する。**リポジトリには置かない。**
4. `ios.yml` に実機向けのジョブを足す。`xcodebuild` は、API キーを渡すと自動署名でプロファイルを作成・更新できる【検索】。アップロードは別の手順にする。`xcodebuild` からの直接アップロードは不安定だという報告がある【検索】。
5. シークレットを使うジョブは手動実行に限り、プルリクエストからは動かさない。
6. iPhone の TestFlight アプリからインストールする。開発チームの内部テスターは 100 人まで登録できる【資料】。

制約: App Store Connect に送るアプリは、2026 年 4 月 28 日以降 Xcode 26 以降でビルドする必要がある【資料】。現在の `macos-latest` は Xcode 26.6 が既定なので満たしている【資料】。

**CI の修正(実機の前にできること)**

- Xcode の版を固定する(§1.5-2)。
- フラグの検査を、表示だけでなく失敗させる形にする(§1.5-3)。
- 3 か所のバージョンが一致することを検査する(§1.5-9)。

**見直す条件**

- Actions からの署名とアップロードが安定しないとき(方法 C、または専用ツールの導入を検討する)。
- 有料登録をしない判断になったとき(iOS は実機検証ができないので、Android だけで先に進める)。

## 5. 横断的な設計

### 5.1 固定時間方式のインターフェース(案)

既存の構造をできるだけ保つ。`Runner` の「ウォームアップ 1 回 + 本計測 5 回」のループ(`runner.cpp:301-331`)はそのまま使い、各回の中身を「固定の仕事」から「固定の時間」に替える。

```cpp
// 案。benchmark_test.h の変更点
struct TestInfo {
  std::string id, name, category;        // category: "cpu_single" / "cpu_multi" / "memory" / "gpu"
  std::int64_t reference_ns_per_unit;    // 基準機 (ピーク段階) の 1 単位あたりの時間
  int window_ms;                         // 窓の長さ (テストの定義の一部)
};

struct Availability {                    // Q8: 実行前の対応確認
  bool supported = true;
  std::string reason;
};

struct RunOutput {
  std::int64_t units = 0;                // 完了した単位数 (全ワーカーの合計)
  double units_per_sec = 0.0;            // ワーカーごとの (完了数 ÷ 実測時間) の合計
  bool checksum_ok = false;              // 完了した全単位のチェックサムが一致したか
};

class BenchmarkTest {
  virtual Availability availability(const TestContext&) { return {}; }
  virtual RunOutput run_for(std::int64_t window_ns) = 0;   // run_once() を置き換える
  // info / setup / before_run / after_run / take_telemetry / teardown は現行どおり
};
```

- **`UnitBasedTest`**: 共有カウンタから取り合う方式(`unit_based_test.h:82-105`)をやめる。各ワーカーが自分の単位を締切まで繰り返し、完了数と「最後の単位が終わった時刻」を返す。
- **`Runner`**: 各窓の `1e9 ÷ units_per_sec` を「1 単位あたりの時間」とし、5 窓の中央値からスコアを出す。安定判定、測り直し、段階の構造は現行のまま使う。
- **基準値**: `reference_times.h` の値を「1 単位あたりの時間」に替える。
- **GPU テスト**: `run_for` の中で、締切まで提出を続け、最後に全提出の完了を待つ。
- **ユニットテスト**: 速さの違うワーカーを模した偽のカーネルで、スループットの推定が偏らないことを確かめる。

### 5.2 JSON の変更(案)

`schema_version` を 6 に上げる。主な変更は次のとおり。

- `tests[]`: `window_ms`、各窓の `units` と `ns_per_unit`、`median_ns_per_unit`、`reference_ns_per_unit`、`status`、`reason` を追加する。`runs_ns` と `median_ns` は廃止する。
- `score_formula`: `"reference_ns_per_unit / median_ns_per_unit * 1000"`。
- `scores.<段階>`: 分野別スコア(`categories`)と重みを追加する。出せないスコアは `null` にする。
- 最上位: 条件の警告の一覧と、比較可能かどうか(`comparable`)を追加する。

Kotlin と Swift のパーサは同時に直す(`BenchmarkResult.kt`、`BenchmarkResult.swift`)。

### 5.3 バージョンの規則(案)

- `benchmark_version` は `MAJOR.MINOR.PATCH` とする。**スコアを比べられるのは、MAJOR と MINOR が同じもの同士だけ。**
- **MINOR を上げる変更**: 計測区間の処理、単位の大きさ、窓の長さと数、代表値の取り方、採用する回を左右する判定、基準値、コンパイルフラグ、分野の重み。加えて、ツールチェーンや変換ツールの更新で生成される機械語・シェーダーが変わった場合。
- **PATCH で済む変更**: 計測区間・手順・基準値に影響しないもの(記録項目の追加、UI、診断モード)。0.1.0 → 0.1.1 がこの例である(`version.h:12`)。
- **MAJOR を上げる変更**: 実測の基準値を入れた版を出した後の、基準機の変更。1.0.0 より前は MAJOR を 0 のままにし、MINOR を上げて表す。
- **2026-11-11 の基準機の変更では、版を上げない(0.2.0 のまま)。** 版は、スコアを比べられる範囲を示すためにある。0.2.0 の基準値は開発用 x86_64 環境の暫定値で、765G の値は一度も入っていない(`core/include/mobilebench/reference_times.h:6-9`)。この変更では、コードも、基準値も、出るスコアも変わらない。新しい基準機の実測値を入れるとき(§8 フェーズ 3)に、基準値の変更として版を上げる。
- `schema_version`(JSON の形)は別に管理する。

### 5.4 GPU テストの計測中表示(方針。実装はまだしない)

**目的**: 計測の様子を画面で見えるようにする。計測の定義は変えない。

**依頼者が決めた要件(2026-11-10)**

1. 計測は、オフスクリーン・固定解像度のまま行う(D4)。
2. アニメーションは経過時間ではなくフレーム番号で進め、全端末で同じフレームを描く。
3. 画面には、数フレームごとに縮小した画像を出す。表示の処理は計測時間に含めない。
4. 表示のあり・なしを切り替えられるようにし、スコアへの影響を比べられるようにする。
5. iOS 版でも同じ方式で実装できる設計にする。

以下は、この要件を満たすための設計の案である。数値はすべて初期値で、実機で確定する。

**(1) フレームの内容はフレーム番号だけで決める**

- 各テストは、フレーム番号 n(0 から始まる整数)だけから、そのフレームのパラメータ(カメラ、物体の姿勢、シェーダーに渡す定数)を求める。時計は見ない。
- パラメータは core の共通コードで、整数の演算か、core に埋め込んだ表から求める。OS の数学ライブラリの関数は使わない。実装の違いで値がずれるのを避けるためである【推測】。
- アニメーションは P フレームで一巡する(P の初期値は 120)。内容は n を P で割った余りで決まる。テストの開始時に n を 0 に戻す。
- 速い端末は、同じ時間でより先のフレームまで進む。フレーム n の内容は、どの端末でも同じである。

**(2) フレームごとの重さを変えない**

固定時間方式は、どの単位も同じ重さであることを前提にする(§4-Q5 の規則 1)。フレームによって重さが違うと、どこまで進んだかでスコアが変わってしまう。そこで、動かしてよいものを「重さを変えない変化」に限る。

| フレーム間で一定にするもの | 変えてよいもの |
|---|---|
| 頂点数、三角形数、描画呼び出し数 | 物体の姿勢、カメラの向き |
| 描画先を覆う画素数(全画面を覆う、など) | 色、模様の位相 |
| シェーダーの反復回数、テクスチャの参照回数 | シェーダーに渡す定数の値 |

それでも、隠れる面の量などでわずかに変わる可能性がある【推測】。フレーム番号ごとの所要時間の差が ±2% に収まることを実機で確かめ、収まらない動きは採用しない(§6 V19)。

**(3) 出力の検証**

フレーム番号が決まれば出力が決まるので、決まった番号のフレームを基準画像と照合できる。計測の後に、照合用の番号のフレームを描いて読み戻し、照合する(計測時間の外)。照合の方法は §4-Q1 の検証 5 と同じである。

**(4) 表示の経路は core を通す(両 OS で共通)**

- core が、オフスクリーンの描画結果を小さな画像(初期値は幅 256 画素)に縮小して読み戻す。画素の配列を、コールバックで UI に渡す。既存の進捗の通知(`ProgressCallback`。`core/include/mobilebench/runner.h:64`)と同じ形である。
- UI は、受け取った画像を表示するだけにする。Android は Bitmap、iOS は CGImage に入れて表示する想定である【推測】。
- 縮小と読み戻しは、描画の抽象層(§4-Q1 の `mb::gpu::Device`)の機能にする。Vulkan と Metal のバックエンドがそれぞれ実装する。UI の層は GPU の API に触れない。この形なら、iOS でも同じ方式になる。
- 採用しない案: 描画結果を UI と共有して直接表示する方法。速いが、OS ごとに別の実装になる。表示の処理が GPU の仕事として計測に混ざる点も問題である。

**(5) 表示の処理を計測時間に含めない方法**

- 表示用の処理は、提出の区切りでだけ行う(§4-Q5 の「M 個の単位をまとめた提出」)。
- 手順は次のとおり。
  1. 提出済みの仕事がすべて完了するのを待つ。
  2. 計測の時計を止める。
  3. 縮小、読み戻し、UI への受け渡しを行う。
  4. 時計を再開し、次の提出に進む。
- スループットは、時計が動いていた時間だけで計算する。窓の長さも、時計が動いていた時間で数える。
- 表示は K 回の提出ごとに行う(K の初期値は 2)。1 回の提出が 20〜50 ms になるように M を選ぶので、表示の頻度は端末の速さによらず、ほぼ同じになる。「数フレームごと」は「M × K フレームごと」に当たる。
- UI への受け渡しは時計を止めている間に行うので、「計測区間の中でブリッジを呼ばない」という制約(`CLAUDE.md`)と矛盾しない。

**(6) 時計を止めても除けない影響**

次の影響は残りうる【推測】。大きさは実機で測る(§6 V18)。

- 時計を止めている間は GPU が休む。周波数が下がったり、温度が下がったりする可能性がある。
- OS の画面合成が、計測中の GPU を使う。
- 読み戻しのたびに、GPU の処理待ちの列が空になる。

**(7) 表示のあり・なしの切り替えと比較**

- アプリの設定で切り替える。JSON には、表示の有無、K、縮小後の大きさ、表示にかけた時間の合計を記録する。
- 「なし」のときは (5) の手順 1〜4 を行わない。それ以外は同じにする。
- 比べ方: 同じ端末で「なし」と「あり」を交互に 5 回ずつ実行し、GPU テストごとにスコアの比を見る。
- **正式なスコアの扱い**(2026-11-10 採用): 基準値は「表示なし」で測る。「表示あり」の結果は、差が受け入れ基準(§4-Q7。変動係数 2%)の範囲に収まると確認できるまで、参考値として扱う。確認できた後に両者を同じ扱いにするかは、依頼者が決める。

**(8) 対象と UI**

- 対象は GPU テストだけである。CPU とメモリのテストには表示を付けない。
- 計測中の画面は、縮小画像の差し替えと最小限の進捗の文字だけにする。動きのある進捗表示は使わない(D4 の注意点)。

- lavapipe(ソフトウェア実装の Vulkan): <https://www.phoronix.com/news/Lavapipe-Vulkan-1.2>

**確認できなかったもの(本文で【推測】と記した主な点)**

- Apple clang の既定の対象 CPU。
- Qualcomm と Nothing の公式サイトの原文。この調査の環境からは `www.qualcomm.com` と `nothing.tech` に接続できなかった。基準機の仕様は、検索結果の要約に基づく。
- Snapdragon 778G+ の、最速の 1 基を除くコアの周波数。資料によって違う。
- Adreno 642L のドライバが実際に報告する Vulkan の版。
- 基準機の単位時間、速いコアと遅いコアの速度比、8 Elite 搭載機との性能比。LG 端末(765G)との性能比。
- 低精度指定やタイル方式の隠面消去が、GPU ごとの仕事量に与える影響。
- 高性能機で GPU テストが CPU 律速になる条件。
- OS によるメモリのページの大きさの違いが、ランダム参照のテストに与える影響の大きさ。
- TestFlight の内部テスター向け配信に審査が要らないこと、PC なしで登録から配布までを完結できること。
- Android で、画面への出力先なしに Vulkan のオフスクリーン描画ができること。
- OS の数学ライブラリの実装の違いが、フレームのパラメータの値に与える影響。
- 計測中の表示が、GPU の周波数・温度・処理待ちに与える影響の大きさ。
- HONOR 端末のタッチ直後の挙動が、最初のテストに与える影響の大きさ。

## 8. 作業ロードマップ

優先順位の考え方は次の 4 つである。

1. **計測方式を先に固める。** 基準値も、その後のすべての検証も、計測方式の上に成り立つ。
2. **基準値の本測定は 1 回で済ませる。** 計測方式と CPU カーネルが確定してから測る。それまでは暫定値のままにする。
3. **GPU は後半に置き、Android を先に作る。** 作業量が最も大きい。
4. **iOS の実機検証は保留する**(2026-11-10 の決定)。実機が要らない iOS の作業(CI の固定、フラグの検査、コンパイラ差の CI での検証、シミュレータ向けビルドの維持)は、各フェーズで進める。

### フェーズ 0: 土台の整理(スコアに影響しない)

- **依頼者の判断**: 異議 1〜3 と Q1〜Q9 は採用済み。Apple Developer Program は保留。残るのは、`docs/design-policy` から `main` へのプルリクエストのマージである。
- **作業**
  - `ios.yml` で Xcode の版を固定する。iOS にフラグの検査を足す。3 か所のバージョンの一致を検査する。
  - 計測中に前面を離れたら無効にする(Android、iOS。iOS はシミュレータ向けビルドが通るところまで)。
  - 計測スレッドの優先度設定を core に寄せる。iOS の機種情報を補う。
- **実機**: V2、V3、V7 の基準機分(現行の 0.2.0 を Nothing Phone (1) で、診断モードをオンにして 1 回実行すれば、3 つとも確かめられる)。8 Elite 搭載機で V5。LG 端末については V20。
- **完了の条件**: CI が 3 つとも成功する。基準機の診断データが手元にある。
- **版**: 0.2.x(PATCH)。

### フェーズ 1: 固定時間方式への移行

- **作業**
  - `BenchmarkTest::run_for`、`UnitBasedTest`、`Runner`、基準値の形式、JSON(`schema_version` 6)、Kotlin と Swift のパーサ(§5.1、§5.2)。
  - フェーズ 0 のデータから単位の大きさを決める(§4-Q5)。8 Elite 搭載機に合わせた 64 → 16 単位の調整は廃止する(D9)。
  - 速さの違うワーカーを模したユニットテストを足す。
  - 診断モードを新しい方式に合わせる。README を更新する。
- **実機**: V4、V14、V15。
- **完了の条件**: 基準機と 8 Elite 搭載機の両方で、受け入れ基準(ピークの変動係数 2% 以下)を満たす。基準値は暫定のまま。
- **版**: 0.3.0。

### フェーズ 2: CPU カーネルのコード生成を固める

- **作業**

- **完了の条件**: カーネルの最内ループの命令の並びが両 OS で一致する。速度比の差が 3% 以内。これで、D8 の「コンパイラ差の確認」の条件が満たされる。
- **版**: 0.4.0。
